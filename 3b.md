# Phase 3b Project Report: Concurrent Update and Query

## 1. Core Algorithm: Design and Implementation

* **Main Algorithm and Requirements Fulfillment:**
  * Extends the Phase 3a pipeline to process interleaved graph updates (`ADD <src> <dst> <weight>`), SSSP queries (`Q`), and producer delays (`D <ms>`) concurrently while guaranteeing deterministic, snapshot-consistent SSSP results.
  * **Monotonic Versioning and MVCC Visibility:** Every edge stores its creation version: `struct Edge { uint32_t dst; int weight; uint64_t version; };`. Initial edges from `initial.txt` receive version `0`. The producer assigns monotonically increasing versions `1, 2, 3, ...` to each `ADD` and `Q` record in arrival order (`D` records do not consume version slots). A query at version $q$ ignores any edge with `e.version >= q`, ensuring concurrent future updates published to adjacency lists remain invisible to query $q$.
  * **Dual-Queue Architecture and Per-Vertex Reader-Writer Locks:** Instantiates `ConcurrentQueue<T>` twice: `update_queue` drained by `TC` updater threads and `query_queue` drained by 1 query thread. Each source vertex owns a `std::shared_mutex`: updaters take `std::unique_lock` to append edges, while SSSP workers take `std::shared_lock` so multiple query threads can scan the same vertex concurrently without blocking each other.
  * **Version-Applied Gate (`ApplyTracker`):** Because `TC` updaters can complete `ADD` requests out of version order, `ApplyTracker` tracks the highest contiguous completed version `applied_max_` and buffers out-of-order completions in a `std::set<uint64_t> done_above_`. Before running query $q$, the query thread calls `apply_tracker.WaitUntil(q - 1)`, guaranteeing all updates with `version < q` are visible. After query $q$ finishes, it calls `apply_tracker.MarkDone(q)` so `applied_max_` can advance past the query's version slot.
  * **Incremental vs. Full Parallel BSP SSSP:** Reuses the Phase 2c lock-free sparse push BSP (`AtomicSparseSssp` semantics) with `TQ` worker threads, C++20 `std::atomic_ref<int64_t>` CAS relaxation on `dist[]`, `std::atomic_ref<uint8_t>` CAS deduplication on `in_next[]`, prefix-sum + parallel `std::memcpy` frontier compaction, and $O(|F|)$ snapshot synchronization into `dist_prev[]`.
    * **Incremental Mode:** Allocates `dist[]` and `dist_prev[]` once and persists them across queries. Because the graph is add-only, shortest-path distances are monotonically non-increasing. The producer records the `src` vertex of every `ADD` into `pending_dirty` (seeded with `{0}` before the first query) and transfers it into each `QueryReq3b`. The query thread deduplicates `dirty_sources` in place and uses it as the initial BSP frontier.
    * **Full Mode:** At every `Q`, resets `dist[]` and `dist_prev[]` to `INF`, sets `dist[0] = dist_prev[0] = 0`, and runs BSP from `{0}` using the same version filter, shared locks, and `ApplyTracker`.
* **Key Source Files and Functions:**
  * `class ApplyTracker` in `main.cpp`: Implements `MarkDone(v)` and `WaitUntil(target)` to barrier queries behind out-of-order updater completions.
  * `size_t RunBspSsspParallel(...)` in `main.cpp`: Executes push-style parallel BSP over versioned adjacency lists using `TQ` threads, per-vertex `std::shared_lock`, `e.version >= q_version` filtering, and `std::atomic_ref` CAS updates.
  * `Phase3bResult RunPhase3b(...)` in `main.cpp`: Pre-loads the version-0 graph, spawns `TC` updaters and 1 query thread before timing, dispatches pre-parsed records with `pending_dirty` tracking, records per-query timings and signatures, and measures the end-to-end window.

## 2. Problems and Solutions

* **Problem 1: C++20 `std::atomic_ref` Compilation Failure Under Default System Compiler**
  * **Problem:** Compiling `main.cpp` with the default system `g++` on `xe-10` (GCC 8.5.0) failed with `error: 'atomic_ref' is not a member of 'std'`.
  * **Cause and Solution:** `std::atomic_ref` (used to match Phase 2c's lock-free sparse SSSP semantics on plain `std::vector<int64_t>` distance arrays) was introduced in C++20 and requires GCC 10 or newer. On RHEL 8, `/usr/bin/g++` is pinned to GCC 8.5.0 while newer compilers are provided via Software Collections. We enabled `gcc-toolset-15` (`scl enable gcc-toolset-15 bash`) and compiled with `-std=c++20`.
  * **Verification:** Compiled with zero errors or warnings and passed the built-in self-test suite (`ALL SELF-TESTS PASSED!`).
* **Problem 2: Deterministic Snapshot Isolation Under Concurrent Out-of-Order Updaters**
  * **Problem:** With `TC > 1` updaters running concurrently with the query thread, two hazards occur: (i) an updater holding an older version `< q` may not yet have appended its edge when query $q$ starts, and (ii) an updater holding a newer version `> q` may already have appended its edge before query $q$ scans that vertex.
  * **Cause and Solution:** Both hazards are eliminated by combining two mechanisms: `ApplyTracker::WaitUntil(q - 1)` prevents query $q$ from starting until every `ADD` with version $< q$ is committed, while the edge-level cutoff `if (e.version >= q_version) continue;` filters out any already-published future edges. Additionally, `std::shared_mutex` prevents iterator invalidation if an updater reallocates `adj[u]` while a query worker is scanning `adj[u]`.
  * **Verification:** Both Incremental and Full modes matched `Archive3b/expected_queries.txt` across all 5 queries for every tested `(TC, TQ)` combination.

## 3. Experimental Results and Analysis

* **Setup:**
  * **Environment:** University of California, Riverside Compute Server Node (`xe-10`).
  * **Architecture:** Multi-core enterprise Linux x86_64.
  * **Compiler and Flags:** GCC 15 (`scl enable gcc-toolset-15`), `g++ -std=c++20 -O3 -pthread main.cpp -o phase3`.
  * **Dataset:** `soc-LiveJournal1` weighted graph (~4.8 million vertices; ~69 million total edges) split into `Archive3b/initial.txt`, `Archive3b/updates.txt` (interleaved `ADD`, `Q`, and `D` records with 5 queries), and `Archive3b/expected_queries.txt`.
  * **Source Vertex:** Vertex `0`.
  * **Commands:**
    * `./phase3 3b both Archive3b/initial.txt Archive3b/updates.txt 2 2 queries.out Archive3b/expected_queries.txt`
    * `./phase3 3b inc Archive3b/initial.txt Archive3b/updates.txt 2 2 queries_nowait.out Archive3b/expected_queries.txt --no-wait`
    * `./phase3 3b inc Archive3b/initial.txt Archive3b/updates.txt <TC> <TQ>` for `(1, 4)`, `(4, 1)`, and `(4, 4)`
  * **Timing:** Measured using `std::chrono::steady_clock` strictly across the producer-consumer window, starting immediately before the producer dispatches pre-parsed records (with `TC` updaters and 1 query thread already spawned and parked) and stopping after all threads join. Query results are buffered in memory and written to `queries.out` after the timer stops.
* **Correctness:**
  * For every query at version $q$, the output signature was computed as $S = \left(\sum_{v : \text{dist}[v] \neq \infty} \text{dist}[v]\right) \bmod (10^9 + 7)$.

## 4. Discussion

* **Question 1:** Compare the times. Which is faster? Why? You can measure each query separately to get a detailed picture.
  * **Incremental** (`12.9095 s`) is $3.57\times$ faster than **Full** (`46.1163 s`) at `TC = 2, TQ = 2`.
  * In **Full** mode, every one of the 5 queries resets all ~4.8 million entries of `dist[]` and `dist_prev[]` to `INF` and re-explores the entire reachable graph from vertex `0`, costing an average of `9047.49 ms` per query (`max = 9565.18 ms`, 208 total BSP rounds).
  * In **Incremental** mode, only the very first query pays the full cold-start traversal cost (`max = 8581.55 ms`). Because edge additions can only decrease shortest-path distances, subsequent queries retain the cached `dist[]` array and seed their frontier strictly with the deduplicated `dirty_sources` modified since the previous query.
  * Most new edges either fail to improve existing distances or only trigger localized relaxations, cutting the average cost of the 4 subsequent queries to `~849.5 ms` each (`3397.95 ms` total across all 4 queries) and reducing total BSP rounds to 143.
* **Question 2:** Skip the `WaitUntil` call in the query thread. Does the output still match `expected_queries.txt`? Do repeated runs produce the same numbers? Explain what you observe.
  * **Result:** Skipping `apply_tracker.WaitUntil(req->version - 1)` (`--no-wait`) causes verification to **fail on every query**. The table below compares `queries.out` (verified against `expected_queries.txt`) against `queries_nowait.out`:

| 689999 | 48154636 | 48499111 | +344,475 |

  * **Determinism:** Repeated runs do **not** reliably produce the same numbers. Because the query thread no longer waits for `TC` updaters to commit all `ADD`s with `version < q`, the exact subset of edges visible when a query worker scans `adj[u]` varies from run to run based on non-deterministic OS thread scheduling and queue drain timing between the producer, updaters, and query workers.
  * **Explanation:** Every query in `queries_nowait.out` is strictly inflated above the true shortest-path sum because missing `ADD` edges with `version < q` prevents the query from discovering shorter paths introduced before version $q$, leaving vertices with larger (stale) distances.
  * **Lingering Error Across Consecutive Queries:** The exact same residual error persists across consecutive queries (`+2,088` on both `1379999` and `1380100`, and `+194` on both `2070001` and `2760002`). In incremental mode, once a `dirty_sources` entry is consumed by a query before its edge lands in `adj`, subsequent queries never re-seed that source vertex unless a later update touches it, causing missed updates to linger across future queries.
* **Question 3:** Try different `TC` / `TQ` combinations on the incremental version and report any findings: where does the time go, what looks like a bottleneck, and any ideas you have for improving the performance.
  * **Where the Time Goes:** In every tested configuration, SSSP query execution dominates total runtime, accounting for `87.2%` of wall time at `(TC=1, TQ=4)` (`6.76 s / 7.75 s`), `92.8%` at `(TC=2, TQ=2)` (`11.98 s / 12.91 s`), and `96.6%` at `(TC=4, TQ=1)` (`25.70 s / 26.61 s`). Non-query time (update ingestion, queue/tracker overhead, and producer `D` delays) stays nearly flat at `0.91 s` to `1.17 s`.
  * **Primary Bottleneck:** Query parallelism (`TQ`) is the dominant performance lever. Increasing `TQ` from `1` to `4` cuts wall time from `26.6080 s` (`TC=4, TQ=1`) to `7.7525 s` (`TC=1, TQ=4`), a $3.43\times$ speedup. Conversely, increasing `TC` beyond 1 slightly hurts performance (`TC=1, TQ=4` at `7.7525 s` beats `TC=4, TQ=4` at `8.0706 s`) due to `update_queue` mutex contention (as seen in Phase 3a), `ApplyTracker::mu_` contention on `MarkDone`, and extra contention on per-vertex `shared_mutex` locks and CPU cores alongside the `TQ` BSP workers.
  * **Ideas for Improving Performance:**
    * **Persistent BSP Thread Pool:** Reuse a fixed pool of `TQ` worker threads across BSP rounds instead of spawning and joining `std::thread` objects on every round (143 round barriers per run).
    * **Batched Update Ingestion:** Apply Phase 3a's `PushBatch`/`PopBatch` optimization to `update_queue` and batch version-range completions in `ApplyTracker` to reduce mutex contention when `TC > 1`.
    * **Dynamic Work Distribution in BSP:** Partition the active frontier dynamically (or by out-degree rather than vertex count) across `TQ` threads to prevent load imbalance caused by high-degree hub vertices in `soc-LiveJournal1`.
    * **Direction-Optimizing (Push/Pull) First Query:** Switch to pull-based relaxation during dense middle rounds of query #0 (when the active frontier covers a large fraction of the graph) to reduce atomic CAS contention on `dist[]`.
