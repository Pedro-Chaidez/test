# Phase 3a Project Report: Graph Update

## 1. Core Algorithm: Design and Implementation

* Main Algorithm and Requirements Fulfillment:
  * Implements a concurrent producer-consumer graph update pipeline that ingests a stream of weighted edge additions (ADD <src> <dst> <weight>) interleaved with slow-producer delay markers (D <ms>) while mutating an in-memory adjacency-list graph.
  * Graph Storage and Per-Vertex Locking: The graph is represented as an out-neighbor adjacency list std::vector<std::vector<Edge3a>> paired with a parallel std::vector<std::mutex> (one mutex per source vertex). Applying an ADD acquires locks[src], executes adj[src].push_back({dst, weight}), and releases the lock so updates targeting distinct source vertices proceed in parallel without contention.
  * Concurrent Queue: Implements an unbounded, blocking, thread-safe FIFO queue (ConcurrentQueue<T>) backed by a std::deque<T>, a single std::mutex, a std::condition_variable, and a closed_ flag.
    * Push(T) inserts an item under the mutex and wakes one parked consumer via notify_one().
    * Pop() -> std::optional<T> blocks via cv_.wait(lock, [this]() { return !data_.empty() || closed_; }). Once Close() is called and the queue is drained, Pop() returns std::nullopt so every consumer exits cleanly.
    * Close() sets closed_ = true under the mutex and calls notify_all() to wake all parked consumers.
  * Batched Queue Extension (Discussion Q2 Optimization): Extends ConcurrentQueue<T> with PushBatch(std::vector<T>&&) and PopBatch(size_t max_batch), amortizing queue mutex acquisitions and condition-variable notifications across batches of 64 requests.
  * Pre-Loading and Producer-Consumer Execution: Before starting the timer, initial.txt is pre-loaded into adj, and updates.txt is pre-parsed into parallel adds[] and delays[] arrays. All N consumer threads are spawned prior to timing so they are already parked on the empty queue. The single producer iterates adds[] and delays[] in lockstep, sleeping locally on D markers without enqueuing them, then calls Close() and joins all consumers.
* Key Source Files and Functions:
  * template <typename T> class ConcurrentQueue in main.cpp: Provides Push, Pop, PushBatch, PopBatch, and Close using std::mutex and std::condition_variable.
  * ParseInitialFile and ParseTraceFile in main.cpp: Pre-load the initial edge list and pre-parse ADD/D records into memory outside the timed window.
  * Phase3aStats RunPhase3a(initial_edges, trace, num_vertices, num_consumers, batch_size) in main.cpp: Initializes the adjacency list and per-vertex mutexes, spawns N consumers, executes the timed producer-consumer window, and computes the verification weight sum modulo 10^9 + 7.

## 2. Problems and Solutions

* Problem 1: Consumer Deadlock During Shutdown on an Empty Queue
  * Problem: If Pop() waits only on !data_.empty(), or if Close() calls notify_one() instead of notify_all(), parked consumer threads can remain blocked indefinitely after the producer finishes and closes the queue.
  * Cause and Solution: With N > 1 consumers, multiple threads may be sleeping on the condition variable when the producer exhausts adds[]. We ensured the wait predicate checks both !data_.empty() || closed_, that Pop() returns std::nullopt when data_.empty() after wakeup, and that Close() calls cv_.notify_all() after setting closed_ = true under mtx_.
  * Verification: Verified clean termination with zero hangs across both the built-in self-test (N = 1, N = 4, batched N = 4) and all Archive3a runs.
* Problem 2: Severe Queue Mutex Contention at N = 4
  * Problem: Running the standard per-item queue with N = 4 consumers slowed execution from 1.2810 s (N = 1) to 3.4820 s (N = 4), a 2.72x slowdown.
  * Cause and Solution: Because applying a single edge takes only tens of nanoseconds, all 5 threads (1 producer + 4 consumers) heavily contended on the single ConcurrentQueue::mtx_ across all 3,448,971 Push/Pop operations. We added PushBatch and PopBatch(64) to transfer 64 items per lock acquisition, and flushed the producer's partial batch immediately before each D sleep marker so consumers continue applying edges during producer stalls.
  * Verification: Re-running N = 4 with batch_size = 64 reduced wall time from 3.4820 s to 0.4532 s while producing the exact same weight sum (834418737).

* Setup:

  * Timing: Measured using std::chrono::steady_clock strictly across the producer-consumer window, starting right before the producer iterates adds[]/delays[] (after consumers are already spawned and parked) and stopping after every consumer thread has joined. Graph pre-loading and trace pre-parsing are excluded.
* Correctness:
  * After all consumers joined, the total edge weight sum modulo 10^9 + 7 was computed over all vertices and out-edges as S = (sum over all v and e in adj[v] of e.weight) mod (10^9 + 7).
  * Every configuration (N = 1, N = 4, and N = 4 with batch_size = 64) produced S = 834418737, matching the expected reference value 834418737 exactly.

### Phase 3a Producer-Consumer Wall Time and Speedup

* Baseline: Single-Consumer Execution (N = 1, batch_size = 1).

| Consumers (N) | Configuration | Wall time (s) | Speedup vs. N = 1 | Weight Sum mod (10^9 + 7) |
| ---: | :--- | ---: | ---: | ---: |
| 1 | Per-item queue (batch = 1, Baseline) | 1.2810 | 1.00x | 834418737 |
| 4 | Per-item queue (batch = 1) | 3.4820 | 0.37x | 834418737 |
| 4 | Batched queue (batch = 64, Q2 opt.) | 0.4532 | 2.83x | 834418737 |

* Analysis:
  * Unbatched Scaling Degradation: Increasing consumers from N = 1 to N = 4 degraded performance by 2.72x (1.2810 s to 3.4820 s) because the single queue mutex serializes all enqueue and dequeue operations while adding multi-core lock contention.
  * Batched Speedup: Batching 64 requests per queue operation reduced wall time to 0.4532 s, achieving a 2.83x speedup over the single-threaded baseline and a 7.68x speedup over unbatched N = 4. Because the trace also contains 5 fixed D sleep intervals that cannot be parallelized, the observed 2.83x speedup approaches the practical Amdahl limit for 4 consumers on this trace.

## 4. Discussion

* Question 1: Which is faster? Explain the result: where does the time go in the slower version? why?
  * N = 1 (1.2810 s) is significantly faster than unbatched N = 4 (3.4820 s), roughly 2.72x faster.
  * In the N = 4 version, the majority of time is spent in synchronization overhead on ConcurrentQueue::mtx_ and ConcurrentQueue::cv_ rather than actual graph updates.
  * Each ADD performs minimal work (acquiring a per-vertex mutex and appending a small struct to a vector). Because every single request must pass through the shared queue mutex twice (once in Push, once in Pop), having 5 threads (1 producer + 4 consumers) hammer the same mutex 6.9 million times causes severe cache-line bouncing across cores, lock handoff stalls, and kernel futex sleep/wake syscalls.
  * With N = 1, contention is far lower and the queue mutex stays hot in cache between just two threads.
* Question 2 (Optional): Based on your analysis in Question 1, propose one change to the queue or its API that would let the four-thread version beat the single-thread baseline. Implement your proposal, then re-run the four-thread pipeline on the same trace, report the performance, and give your analysis.
  * Proposal: Add batched enqueue and dequeue operations (PushBatch(std::vector<T>&&) and PopBatch(size_t max_batch)) to ConcurrentQueue<T>. The producer buffers up to B = 64 ADD requests into a local vector (flushing immediately before any D sleep marker) and pushes the entire batch under one mutex acquisition. Each consumer pops up to B = 64 requests under a single mutex acquisition and then applies all 64 updates independently using per-vertex locks.
  * Measured Performance: With N = 4 and batch_size = 64, wall time dropped from 3.4820 s (unbatched N = 4) and 1.2810 s (N = 1 baseline) down to 0.4532 s (2.83x faster than N = 1, 7.68x faster than unbatched N = 4), with verified weight sum 834418737.
  * Analysis: Batching reduces the number of queue mutex acquisitions and condition-variable wakes by a factor of 64x (from ~3.45 million pushes to ~53.9 thousand batch pushes). Once the queue lock is removed from the per-edge hot path, the 4 consumer threads spend their time executing parallel adj[src].push_back(...) calls across disjoint source-vertex mutexes, allowing N = 4 to decisively beat the single-consumer baseline.
